# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What's here

Several loosely coupled programs share one repo:

| Part | What it is | Entry point |
|------|-----------|-------------|
| `docs/` | The visualizer as a single-file web app (Web MIDI, Chromium only). Deployed to GitHub Pages on push to `main` when `docs/**` changes. No build step. | `docs/index.html` |
| `midi_coach/` | Python MCP server for Claude Desktop: records the keyboard, grades takes against a reference, writes sheet music, runs the coach page and the voice "Maestro". All active development is here. | `python -m midi_coach` |
| `src/` + `main.py` | Older pygame desktop version of the visualizer (pywebview overlays for OSMD sheet music and WebGL fluid, HTTP control panel on :8181). | `Launch Piano MIDI Visualizer.bat` |
| `server/` | Node audience-vote server (Kik webhook, WebSocket to the visualizer and `docs/overlay.html`). | `node server/server.js` |
| `firmware/` | ESP32 FastLED bridge for the LED strip (serial/BLE frame protocol is in the README). | Arduino sketch |

`reference/` (downloaded band MIDI library) and `config.json` are gitignored; `config.example.json` is the template.

## Commands

Windows, from the repo root, using the repo's `.venv`:

```bat
.venv\Scripts\python -m pytest midi_coach/tests                    :: full suite, ~50 s, no hardware needed
.venv\Scripts\python -m pytest midi_coach/tests -k <name>          :: one test
.venv\Scripts\python -m pytest midi_coach/tests/test_sheet_conventions.py

.venv\Scripts\python -m midi_coach.practice [piece]                :: coach page without Claude Desktop (http://127.0.0.1:8765/)
.venv\Scripts\python -m midi_coach.engraving <score.musicxml> --png <out_dir>   :: lint a score + render worst bars
.venv\Scripts\python -m midi_coach.render <score.musicxml> <out.png> [first last] :: render bars with OSMD in headless Chrome/Edge
.venv\Scripts\python -m midi_coach.songs "<song title>" ...        :: build song lessons from the reference library
.venv\Scripts\python -m midi_coach.atlas.build                     :: rebuild the Roadmap from <home>/atlas/content/syllabus.json
.venv\Scripts\python -m midi_coach.atlas.first_steps               :: rebuild + write the First steps / Ready to read / Familiar tunes lessons
.venv\Scripts\python -m midi_coach.atlas.generate --tiers initial,g1,g2 [--dry-run]  :: batch-write theory lessons on the subscription
.venv\Scripts\python -m midi_coach.atlas.pan                       :: rebuild the flute Roadmap
.venv\Scripts\python -m midi_coach.atlas.sax                       :: rebuild the alto saxophone Roadmap
.venv\Scripts\python -m midi_coach.atlas.voice [high|low]          :: rebuild the vocal Roadmap (both voices by default)
.venv\Scripts\python -m midi_coach.atlas.fiddle                     :: rebuild the fiddle Roadmap (likewise .guitar, .bass)
```

There is no linter or formatter configured. Tests use a fake `rtmidi` and synthetic performances; `conftest.py` fails any test that tries to open a browser. `test_sheet_conventions.py` skips songs that aren't in the local `reference/` folder.

## midi_coach architecture

**Note model (`notes.py`).** Everything loads into a flat, seconds-based `Score` of `Note`s, with parts split by MIDI track + channel (matching the web visualizer's track list) and bars derived from the file's time-signature and tempo maps. Part/hand selection (`playable_parts`, `select_notes`, `suggest_hands`, `effective_hands`) lives here too; the user's confirmed choice is saved per file in `<home>/part_choices.json` via `library.py` and every downstream feature (grading, playback, sheet, Learn Mode) reads it.

**Grading.** `analysis.py` groups onsets into chords and aligns take vs reference with dynamic programming, then scores notes/timing/tempo/dynamics/articulation/pedal. `live.py` runs the Synthesia-style `wait` and `rehearsal` modes in real time and pushes cursor/marks to the display. `remarks.py` turns a graded pass into the Maestro's spoken feedback.

**Sheet-music writers.** `transcribe.grand_staff` is the shared MusicXML writer. Callers: `transcribe.py` (takes → lessons), `sheet.py` (piano sheet for a band MIDI, cached in `<home>/derived`), `songs.py` (vocal line over the piano part), `lessons.py` (tinyNotation / MusicXML / excerpts). `details.py` writes chord symbols, Roman numerals, lyrics and section names into whatever sheet the page draws (the coach page's *Add chords & lyrics*), from the notes and then from a subscription lookup, cached in `<home>/derived/details`; it never touches a note. `regrid.py` recovers a beat grid for MIDI files whose notes drift off their own bar lines; it changes notation only, never note times. `playable.py` is the page's **Clean** (Sheet → This sheet): an opt-in, per-file pass (`library.playable_chosen`) that makes the hands' parts playable — a key sounded twice played once, notes out of reach handed to the other hand (`Note.hand`), what no hand reaches left out — so it is the one place notes are removed, and only because the user asked. `engraving.py` holds `RULES`, readability checks run on what the reader sees.

**Display (`display.py`).** A localhost HTTP server (port 8765) pushes state over Server-Sent Events. Two front ends consume the same stream, and both render through `docs/notation.html` (the visualizer's OSMD strip): the coach page `midi_coach/static/coach.html`, and the web visualizer's notation strip when connected via Settings → Hardware → Practice Coach. So changes to `docs/notation.html` affect both the coach and the deployed site. The coach page drives runs with `POST /cmd/<name>`, handled by callables registered on `DisplayHub.commands`. Play-along video (`static/video.js` + `synced.py`): a YouTube player on the coach page posts its position as a beat to `cmd/synced_cursor`; the video-to-score map comes from downbeats the user tapped, saved in `<home>/synced.json`. `youtube_extension/` (unpacked Chrome/Edge extension) does the same on youtube.com for videos that refuse embedding, through the same commands; its `content.js` mirrors `video.js`, so change both together. The page's **YouTube** tab (`static/youtube.js`, `cmd/youtube`) shows whether the extension is connected (the display notes its commands by origin / `X-Piano-Coach-Extension` version header; bump `manifest.json`'s version when its files change, so the tab asks for a reload) and lists every synced song.

**Updates and restart (`launch.py`).** The shortcut's launcher runs `midi_coach.practice` as a child process with `MIDI_COACH_RESTARTABLE=1` and starts it again whenever it exits with `launch.RESTART_EXIT` (75). The page polls `cmd/code_status` (`launch.code_times()`: newest settled `.py`/`.json` change vs. the page's `STATIC_FILES`) and shows an update bar: Reload for page files, Restart for code, which is `cmd/restart`. That writes `<home>/restart.json` (the piece on the page, read once by `practice.main`) and exits. The page reloads itself when `started` changes. Claude Desktop's midi-coach isn't restartable.

**MCP server (`server.py`).** Defines every tool (listed in `midi_coach/README.md`) and wires the modules above together. `practice.py` reuses it without Claude Desktop. Only one process can own the MIDI input and display port, so `practice` and Claude Desktop's midi-coach must not run together.

**Maestro (voice).** `chat.py` uses the Claude API (Haiku for conversation/commands, Sonnet for writing lessons) with spend metered to `~/MidiCoach/ai_spend.json` against `MIDI_COACH_DAILY_CAP`. `deep.py` hands teaching questions to headless `claude -p` on the user's subscription, which connects back through a local MCP endpoint (port 8780). `stt.py` (faster-whisper) and `tts.py` (Kokoro) run locally.

**The Roadmap (`atlas/`).** A skill tree on the ABRSM Piano syllabus: tiers (First steps, Ready to read, Initial, Grades 1–8) → strands → families → requirements → stages. A goal's ordered list of families is a **Path**. Use "Roadmap" and "Path" in the UI, the Maestro's words and the manual, for every instrument (it was called "Atlas" for piano and "Pan" for flute); code, folders and stored data keep the old `atlas`/`pan` names. `build.py` turns `syllabus.json` + `templates.py` into `atlas.json` (2,000+ nodes; `layout.py` fixes every position and bundles edges per zoom level); `first_steps.py` adds the coach's own beginner tiers; `familiar.py` adds a *Familiar tunes* family to graded tiers (public-domain songs in `data/familiar_tunes.json`; on the Path, never in a mock exam). `mastery.py` is pure functions over the tree and the event log (Not started → Practised → Proficient → Mastered; stage credit, 30-day rechecks, rings, weakest child), so progress can always be rebuilt; `store.py` keeps the log, goals, temporary nodes and exams in the profile's `atlas/`. `runtime.py` serves the page's Atlas commands and grades each lesson step (`steps.py`). Content: `technique.py`, `sightreading.py`, `aural.py`/`aural_lessons.py`, `pieces.py` (public-domain catalog in `data/pieces.json`, grade estimates from `difficulty.py`), and `generate.py`, which writes theory lessons in batches through `claude_run.py` (headless `claude -p`, model `MIDI_COACH_GENERATOR_MODEL`). `exam.py` + `marking.py` (numbers in `data/marking.json`) run mock exams, `placement.py` chains them to find a level, `planner.py` + `song_facts.py` turn a goal into a Path (with up to five bridge nodes, `temporary.py`), and `drills.py` adds remedial drills for bars that keep slipping. `today.py` plans Home's one-button **Today** session (warm-up, review, the Path's next stop, a piece for fun) sized to the learner's daily minutes. Front end: `static/atlas.js`, `static/today.js`.
- **Copyright:** the repo is public and ABRSM owns its syllabus, so ABRSM-derived data (`syllabus.json`, the built `atlas.json`, generated lessons) lives only in `<home>/atlas/content` (`MIDI_COACH_ATLAS_CONTENT`), never in git. The repo holds the engine, templates, the public-domain tunes and pieces, and made-up sample syllabi in `atlas/sample/` for the tests.
- **The flute Roadmap** (`atlas/pan.py`) is the same engine for the flute. A profile learns one or more instruments (`profiles.py` → `instruments`, the current one `instrument`, switched from Home's buttons) and each keeps its own progress folder (`profiles.atlas_folder()`: `atlas` for the first, `atlas-<instrument>` after); the flute tree is a First notes tier, then ABRSM Flute Grades 1–2, built into `<home>/atlas/pan` from public-domain tunes in `data/pan_tunes.json`. The page pitch-tracks the flute from the mic (`static/flute.js`).
- **Alto sax and vocals** use the same engine: what differs per instrument is a `pan.Course` (`atlas/sax.py`: First notes + ABRSM Saxophone Grades 1–2 into `<home>/atlas/sax`, syllabus drafted locally; `atlas/voice.py`: the coach's own course from `data/voice_syllabus.json` and `data/voice_songs.json`, built into `voice-high` and `voice-low`). `instruments.py` is the one table of what an instrument changes (mic or MIDI, Roadmap folder, the mic's pitch limits, transposition); check it rather than comparing instrument names. Sax scores are written pitch (MusicXML `<transpose>` −9) and graded in written pitch: `flute.js` adds `transpose` to every pitch it hears and takes it off the page's examples. A low voice's scores are an octave down under a treble-8vb clef, stored at sounding pitch, so nothing is shifted. A profile's `voice` (high/low) picks the vocal folder.
- **Fiddle, electric guitar and bass guitar** are the coach's own courses (`atlas/fiddle.py`, `guitar.py`, `bass.py`, syllabi and tunes in `atlas/data`, loaded by `pan.load_own_syllabus`). Guitar and bass scores are written an octave up under a treble-8 / bass-8 clef and stored at sounding pitch (`octave=-12`, like a low voice). The mic hears one note at a time, so guitar chords are Theory lessons, never graded. Instruments with `strings` in `instruments.py` get an optional tab staff: `docs/notation.html`'s `addTab` adds it as an extra part on the page only (`isTabStaff` keeps it out of marks, note names and staff roles), so the server, grading and files never see it.
- **Woodwind fingering** (flute, sax): `docs/fingering.js` holds the charts (keys down per written MIDI note) and draws them as SVG; it is loaded by `docs/notation.html` (Sheet ▸ Fingering: `fingSpec`, `buildFingering`, drawn on the page only, with OSMD spacing rules widened to make room) and by the coach page (Find the notes' read step `fingerings`, quiz steps with `fingering`, and `flute.js`'s monitor fed by the `pending` marks). `pan.fingering_quizzes` writes the ungraded *Which note is this?* steps for `pan.FINGERED` courses.
- Stored level keys stay `practised`; the UI shows "Practiced".

**Bug reports (`bugs.py`).** The user reports app bugs by voice while practising. Reports also come from the coach page's F9 box (`cmd/report`, typed). Each is a folder in `~/MidiCoach/bug_reports/open/` with `report.md` (what they said, practice context, recent log), `state.json` (score path, bar, view, mode, bars, tempo, loop; for the check step's Go there, `cmd/goto_report`; older reports have none and `bugs.place` reads the context instead) and JPEG screenshots (`before-NNs.jpg` = seconds before the report, `now.jpg`, `now-2.jpg`…). When asked to "fix the bug reports" (or "work the backlog"), read each `report.md` (a `## Checked …: still wrong` section means an earlier fix didn't work: read what the user said) and its screenshots, fix the cause in the code, then run `.venv\Scripts\python -m midi_coach.bugs ready <folder name> "<what changed, for the user>" --log <build-log note name>`. That moves it to `bug_reports/check/`, and the user confirms it on the coach page (👀 → Works → `fixed/`, Still wrong → back to `open/`). Never move a folder to `fixed/` yourself. When the user says one needs no fix (not a bug, a request to the Maestro, already works), `python -m midi_coach.bugs close <folder name> "<why>"`. Feature requests ("Idea: …", or the Maestro's `request_feature` tool) are saved the same way to `~/MidiCoach/requests/open/`; when asked to "do the requests", build each, then mark it ready the same way (Works → `requests/done/`). `python -m midi_coach.bugs list` shows every item by stage.

**Triage and batches.** Before fixing anything (and when asked to "triage the backlog"), triage every open item that has no `triage.json`. Read its report and screenshots, find the code a fix would change, then run `python -m midi_coach.bugs triage <id> --area "<area>" --size S|M|L --files <comma-separated repo paths> [--risk "<what else it could break>"] [--after <ids it depends on>] --needs build|question|design`.
- Reuse an area name already in `bugs batches` when one fits: top bar & layout, sheet display, playback & metronome, grading & practice runs, Maestro & voice, Roadmap & lessons, songs & library, microphone instruments, bug reports & tooling. One area per batch, so items changing the same part of the app are done together.
- `--needs question` when building it would mean guessing what the user wants: give one `--question` and two to four concrete `--choice`s. A worker that finds this out while building runs `bugs ask <id> --question "…" --choice "…" --choice "…" --by <you>` (claim given back, triage kept) instead of guessing or `stuck`. The user answers in the 👀 box (`cmd/answer`), to the Maestro ("any questions?" → "answer two"; `server._voice_questions`, no API call) or with `bugs answer <id> <n|words>`: the answer is appended to `report.md` as `## Answered …` (follow it) and the item becomes `build` in its area's batch. `--needs design` for anything that needs a design conversation (a new mode, a new workflow); those are never built unattended.
- Then work `python -m midi_coach.bugs batches` in order: the first batch's items one at a time, important ones first.
- **One worker per item, one commit per fix.** Before touching code, claim the item: `bugs next --by <you>` (the next in batch order) or `bugs claim <id> --by <you>`. A runner's worker takes a whole batch with `bugs take-batch --by <you>`: up to two workers at once, and a batch sharing files with another worker's is skipped. A worker builds in its own git worktree (`fixgit.worktree`, `<home>/workers/<name>` on branch `runner/<name>`, with `MIDI_COACH_REPO` pointing at it), so its `ready` commits stay on that side branch (held under `refs/fixes/<id>`). The user's ✅ cherry-picks the commit onto their branch (it waits, and says why, while they have uncommitted edits in one of its files); Still wrong just drops it. **The runner** (`runner.py`, `python -m midi_coach.runner`, started at login by a scheduled task, `--install`) fills its two slots whenever work is queued: first one worker triages untriaged items (read-only), then each slot takes a batch. Workers are headless `claude -p` runs in their worktree that may only read, edit inside the worktree, run `.venv/Scripts/python` (a junction to the real venv) and read-only git; their prompts are `runner.BUILD` / `runner.TRIAGE`. An item a worker can't finish is marked with `bugs stuck <id> "<why>"` (🧱 in the Backlog, never retried until `bugs unstick`); a usage limit gives claims back and pauses 30 min. Log: `<home>/runner/<date>.log`. Skip anything another worker has claimed. When it's fixed and the tests pass, run `bugs ready <id> "<what changed>" --log <note> --files <the repo paths you changed> --by <you>`. That commits just those files as one commit (never pushed). It refuses a file that had the user's own uncommitted edits when you claimed: then ask the user, don't commit. On the coach page, Still wrong `git revert`s that commit, or flags the report "Needs an agent" if the revert doesn't apply. `bugs release <id>` gives an item back. If you're asked directly to change something while a runner may be working, add it to the queue (F9 / a report) or claim it first. Don't edit alongside. The user marks priority by saying "important bug: …", with F9's ⭐, or `bugs important <id>`. Each change rewrites `Projects/MidiCoach/Backlog.md` in the Obsidian vault (`MIDI_COACH_VAULT`, default `~/Vault`; tests set it `off`). Every exchange with the Maestro is also appended to `~/MidiCoach/maestro_log/<date>.md`; scan it for requests made in passing.

**User data** lives in `MIDI_COACH_HOME` (default `~/MidiCoach`): `takes/`, `lessons/<category>/`, `derived/`, part choices, notes. Lesson categories are folders; `organize_lesson` moves a file and rewrites the takes and part choices that point to it, so don't move lessons with plain file operations.

## Conventions for sheet music

- A messy score is a bug. Before showing any MusicXML the coach wrote, run `midi_coach.engraving` on it (no rule broken, no source note lost) and render the opening and the worst bars to PNG with `midi_coach.render`, then look at them.
- When a new kind of mess turns up, add it to `engraving.RULES` with a regression test and fix the writer, not just the one file.
- Lessons built from a source file keep its pitches, rhythms and parts exactly (Clean, `playable.py`, is the user's own per-file choice on top, recorded in the sheet's `<source>`). Only notation-level cleanup is allowed (grid snapping, clefs, 8va/8vb that keeps the true pitch for grading), and the change is recorded in the MusicXML `<identification><source>`. New song lessons go to the *Needs review* category.
